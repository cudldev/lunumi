# Local menu assistant

The assistant runs in the browser. On first run Lunumi welcomes the user with a short centered pet animation, then shows the preference questionnaire. The user enters the app only after the local model initializes; onboarding shows download progress or a retryable error. A floating Lunumi pet opens a chat backed by Qwen3-0.6B ONNX in a Web Worker through Transformers.js 4.2.0. This runtime is pinned while the reported WebGPU failures are investigated; menu and chat turns also share one serialized inference queue. Lunumi tries WebGPU with q4f16 weights first (about 570 MB), then automatically retries with the same model on WASM CPU using q4 weights (about 920 MB) if WebGPU initialization or inference fails. If a WebGPU error escapes the worker, or WebGPU produces no output for 90 seconds, Lunumi restarts a fresh worker on CPU and automatically retries pending chat or menu requests. CPU fallback is slower; if it also produces no output for 90 seconds, the request stops with a retryable error. Startup stops after four minutes. Chat and menu generations stream activity from the model so the 90-second limit tracks inactivity rather than total generation time. Later visits reuse browser-managed cached weights when retained. The model is a general base model, not fine-tuned on Lunumi's menu examples. A small Cloudflare Worker fetches approved restaurant pages that the static app cannot read because of browser cross-origin rules. Page extraction, OCR, language detection, dietary-label handling, and English, Finnish, Swedish, and French line classifiers run in the browser.

## User flow

1. Opening a restaurant detail checks the device's parsed-menu cache. Otherwise, the menu card shows a live status while it finds a source, reads the restaurant page, interprets menu items, or runs on-device OCR. The first-run profile asks about cuisines, foods to avoid, and dietary requirements; these preferences remain on-device and can guide the local model's menu summary and chat responses.
2. The Worker uses Cloudflare's platform fetch API, accepts only generated allowlisted hosts, follows up to three allowlisted redirects, forwards no restaurant cookies or authorization headers, and returns at most 500,000 bytes of page text, 3 MB of image bytes, or 5 MB of PDF bytes.
3. The browser extracts candidate text from restaurant pages, feeds, PDFs, and clearly labeled menu images. Lightweight evidence rules rank likely menu sources and filter page noise. If the first page is weak, Lunumi checks up to four likely same-site menu links (including price-list labels such as Finnish “hinnasto”) and up to three same-site images clearly marked as menus; optional OCR and selectable PDF text extraction run on the user's device. The local model creates a compact displayed list and summary. Each item's name and any displayed details must be verifiable in its source excerpt. If generation stops mid-response, Lunumi can retain complete item objects only; it discards the incomplete object and omits the summary, then applies the same source-quote validation to every retained item.
4. If the source cannot be read or the AI cannot return verifiable items, the list remains empty and says **Menu not available** with a link to the source.

Tapping the Lunumi pet opens a chat. The chat starts without a canned introduction. A simple greeting makes the pet react with a brief happy animation instead of returning a stock paragraph. Lunumi narrows context to restaurants that match the latest question, or the five nearest listings for a broad question, and includes only short menu excerpts for those restaurants. The pet changes face and mood cues as the user types, while it thinks, after a helpful or uncertain reply, and on errors. Chat text streams as the model produces it, with a speaking-mouth animation and a short message-bubble entrance; reduced-motion settings disable the animation. Menu reading shows when the model begins producing output. WebGPU errors or 90 seconds without GPU output trigger a fresh CPU worker and an automatic retry; the CPU request stops with an error if it produces no output for 90 seconds. Startup and inference errors are shown to the user instead of silently substituting a menu list. It does not perform web search, read Google results, or fetch menu pages as part of chat; open a restaurant menu first to load its source. When an answer names a restaurant, Lunumi attaches directory, official-site, or menu source links matched by restaurant name, when available. Replies may be inaccurate. Verify details with those sources, especially dietary and allergen information.

The pet has a fixed restaurant-and-food persona. A local scope check rejects unrelated requests before model inference, and the model instructions direct it to ignore role changes, requests to expose hidden prompts, and instructions embedded in source pages. Model-special-token strings in user preferences, chat history, and fetched text are neutralized before inference. These controls reduce misuse and prompt injection; a small on-device language model cannot be guaranteed jailbreak-proof, so factual menu claims still require source verification.

## Extraction and labels

Generic HTML pricing tables are extracted row by row. Product names, each available price, and its column label (such as “Ateria” or “Hampurilainen”) stay together; category headings label the rows. This keeps meal and item prices distinct without a per-restaurant parser.

When the fetched page publishes Schema.org restaurant metadata, Lunumi can show its name, description, and cuisine labels; the page's title or description metadata are used when richer restaurant metadata is absent. The same overview lists the extracted menu count and printed section names, plus the selected restaurant listing's brief address when available. Separate links point to the restaurant page and address source. These are source-based summaries, not generated claims, and missing details are left unstated.

For mixed-language pages, a secondary language classifier can rescue a candidate only when it is highly confident and the line itself has stronger language clues for that language than for the page's primary language.

The source reader and lightweight line classifiers help locate and compare candidate menu pages; they do not supply the displayed item list. The on-device language model creates the displayed summary and items. Each displayed item must include an exact source excerpt containing its name; sections, descriptions, prices, ingredients, allergen notes, and dietary information are accepted only when they appear in that excerpt. Lunumi never infers that an item is safe for a diet or allergy. If the model cannot return verifiable menu items, the list stays empty and says **Menu not available** with the source link; Lunumi does not fall back to showing raw page-extracted rows. Model output remains subject to mistakes, so users should open each item's source text and verify dietary or allergen details with the restaurant.

The source reader skips recognized restaurant-story, values, booking, gift-card, and private-event sections when it scores possible menu sources. Restaurant location headings and nearby opening-hours, address, and postal-code lines are excluded as well. It reads matching content panels from collapsed accordions without requiring the user to open them, but only uses panels with menu headings or priced rows. It also treats lunch-list and weekday/date toggles as headings, and filters sentence-like marketing copy. Structured entries must include menu context or item details, or receive a high-confidence dish prediction from a local language classifier; schema markup by itself does not make a page label a dish. Category-only headings are excluded across the supported languages even when they appear inside structured data. The assistant compares likely menu sources by their price, section, and item-detail evidence when the initial page is weak. These rules are conservative heuristics; unusual pages may still need improved extraction.

Items may include a section, name, nearby description, price, ingredients, explicit dietary or allergen information, source excerpt, and an official source image. The reader recognizes Schema.org `Menu`, `MenuSection`, and `MenuItem` JSON-LD; it also reads supported product cards and falls back to semantic headings, paragraphs, and list items. Repeated trailing prices in structured item names are moved into the price field, trailing separators are removed when a structured price is supplied separately, and structured dotted dietary-code rows are attached to the preceding dish. On menu pages with a clear menu title, h1/h2/h3 headings become section labels and the category index between the title and the first section is omitted. Compact headings containing three or more repeated price pairs are split into separate items, trailing separators before prices are removed from names, and dotted dietary codes beside a price stay attached to the previous item. For tabbed menus, it matches the selected tab to a panel by ID (even when accessibility roles are absent), or uses the currently visible/current-weekday panel, then extracts dish rows and attached details instead of treating the whole restaurant page as menu text. Static lunch pages that group dish rows under weekday/date headings are extracted from their content region, keeping navigation and form text out of the menu list. Same-site PDF links with menu clues are read with Mozilla PDF.js 6.4.299 (Apache-2.0), loaded on demand from jsDelivr; it extracts selectable text in the browser, up to 20 pages and 120,000 characters. For PDFs with tracked text, spaced glyphs are rejoined; centered uppercase rows are treated as section headings, and long priced detail rows are attached to the preceding dish. Scanned/image-only PDFs are not OCR'd. A result needs evidence of an actual menu, such as a menu-specific source URL or heading, or explicit item details like price, ingredients, dietary, or allergen data. A section or image alone is not enough. Generic home-page text like contact details or marketing copy is rejected, allowing same-site menu-link and labeled-image discovery to continue. The parser recognizes section names across supported languages even when language detection is uncertain; this includes Finnish category-only headings such as “Lastenruoat.” When a known heading and dish share one line, it separates the section while keeping the original source line for verification. Explicit ingredient, dietary, or allergen lines immediately following a dish are attached to that dish and kept in its source excerpt; page-wide warnings, including general Finnish staff guidance about allergen questions, remain menu notes rather than dish items. It skips common lunch-page metadata and interface text, including nutrition panels, carbon-footprint lines, opening hours, weekday navigation, past/no-lunch status, date-validity labels, and upload or feedback prompts. Short dietary codes remain visible as printed. Lunumi expands a code only when that same source page supplies its legend, including inline definitions such as G = Gluteeniton or VEG: Kasvis; it does not guess code meanings across restaurants. A small character n-gram classifier filters likely non-menu text. English uses 234 KB weights trained from USDA FoodData Central FNDDS data (CC0), NYC DOHMH MenuStat historical items (NYC Open Data), and Lunumi-authored CC0 page-noise examples; the weights are requested in browser idle time unless data saver or a 2G connection is reported. The City of New York provides its MenuStat data as-is without warranties of completeness or accuracy; Lunumi credits the source when the English filter is used. Finnish and Swedish use weights trained from Fineli CC BY 4.0 food names, synthetic menu-line combinations, and CC0 page-noise examples; matching weights load after language detection. When the page has strong clues for a second supported language, Lunumi loads that language’s classifier too unless data saver or a 2G connection is active. A high-confidence alternate-language dish prediction preserves a candidate the main classifier would reject; if the secondary model is unavailable, priced candidates are retained. This protects mixed-language menus without a restaurant-specific rule. The assistant links to Fineli and credits THL when those models are used. These small classifiers judge candidate lines, not whole pages, and their food-name data does not prove restaurant-menu extraction accuracy. For clearly labeled menu images, Tesseract.js OCR runs locally using the detected Finnish, Swedish, or English fast model; its code is Apache-2.0. The OCR code and selected language data remain on demand: the first OCR use downloads several megabytes for the engine and one language. Language data comes from a pinned `tessdata_fast` revision via jsDelivr and is cached by the browser. The image and recognized text are not sent to those CDNs. Dietary tags, ingredients, and allergen notes are shown only when explicitly stated in source data. The assistant does not infer allergy safety. Extraction and OCR are heuristic and may miss or misread entries. A restaurant may block the Worker (for example, with HTTP 429); in that case the app keeps the menu empty and links to the source.

The bundled Finnish and Swedish weights use Fineli CC BY 4.0 food names and Lunumi-authored CC0 synthetic page-noise examples; the assistant links to Fineli and credits THL when those weights are used. These examples are not restaurant menus and do not provide dietary or allergen facts.

## Privacy, cache, and limits

- The Worker processes requested URLs, page text, or bounded image/PDF bytes in transit. It sends no credentials, does not persist menu content, and uses `Cache-Control: no-store`. PDF parsing and OCR run on the device; PDF bytes, images, and extracted text are not sent to the PDF.js or OCR package hosts.
- Parsed items and source excerpts are cached in browser local storage for 24 hours, up to 20 URLs. The parsed cache uses a versioned key; parser updates advance it to trigger a fresh page read. When that cache misses, the app fetches the current page; raw source text in IndexedDB is used only as a stale fallback if fetching fails, for up to seven days. Both caches stay on the device and are removed by clearing Lunumi site data. Daily menus split across `<br>` lines are preserved as separate items, including longer dish descriptions, and source navigation/form links are excluded from extracted dish text.
- Chat messages, preferences, and model inference stay on the device. The model runtime is loaded from jsDelivr and pinned model weights are downloaded from Hugging Face; no menu text or prompt is sent to those hosts. The Qwen3 q4f16 WebGPU weights are about 570 MB; if GPU initialization or inference fails, the same model retries on WASM CPU with q4 weights (about 920 MB and slower). Browser-managed model cache can be evicted. No model API or per-request inference charge is used.
- Worker requests are capped at 100,000 per day on Cloudflare's free plan. Hosts must be in the allowlist; restaurants may still block requests.
- Worker fetch timeout is 10 seconds; browser timeout is 15 seconds and each search reads at most five pages. PDF.js and its worker are loaded from jsDelivr on first PDF use, so the first open needs an internet connection; the document itself stays on-device during text extraction. Text-based PDFs up to 5 MB and 20 pages are supported; image-only PDFs are not OCR'd. OCR supports clearly labeled same-site menu images up to 3 MB; unlabeled images are not OCR'd. The OCR engine is lazy-loaded and may take extra time on first use; JavaScript-only content may be missing from returned HTML. Product images are loaded directly from the approved HTTPS source host; Hesburger's official `fi-www.hesburger.net` image host is also allowed. Other third-party image hosts are omitted.
- The English classifier's 90.4% item-group-held-out accuracy is a food-vocabulary/page-noise check, not a restaurant-menu evaluation. French weights use restaurant-held-out CROUS lines from one public dataset; this checks French item/section filtering, not extraction quality on arbitrary restaurant pages. Either classifier may suppress valid dishes.

## Setup and deployment

The static app reads `VITE_MENU_READER_URL` at build time. Set GitHub Actions repository variable `MENU_READER_WORKER_URL_STAGING` to the deployed Worker URL ending in `/v1/menu`; leave the live URL unset until Staging is verified.

The Staging Worker deploy runs from `staging` when `MENU_READER_DEPLOY_ENABLED=true`. It builds the host allowlist from the `staging` branch of `cudldev/finland-restaurant-data`, matching the Staging Pages directory. It uses the repository variable `CLOUDFLARE_ACCOUNT_ID` and the GitHub Actions secret `CLOUDFLARE_API_TOKEN`; keep the token only in GitHub Actions Secrets. The existing Worker uses Cloudflare's free request tier and has a 100,000-request daily cap.

The GitHub Pages workflow builds the live and Staging sites from their respective branches, then publishes the artifact to the free GitHub Pages site through the `github-pages` environment.

## Restaurant directory data
The GitHub Pages workflow builds the live directory from the `main` branch of `cudldev/finland-restaurant-data` and the Staging directory from that repository's `staging` branch. Staging-only source changes stay out of the live directory until they are separately promoted to `main`. The directory stores source URLs and provenance; it does not copy restaurant menu content. Both repository branches are public and use the existing free GitHub Pages workflow.
